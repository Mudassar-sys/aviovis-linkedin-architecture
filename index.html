Architecture Overview

A control plane for profile workspaces: where they run, who can open them, how sessions are handled, and how problems surface before they stop the team. Nothing here is deployed yet. The paid pilot builds it on real test infrastructure and measures it.

N
Registered workspaces
100, 250 or 500. Drives storage and stored profile licences.
C
Peak active at once
Drives servers and runtime licences. Measured in the pilot, never assumed as a fixed percentage.
U
Named human operators
Drives seats, identity, training and support. Not equal to N.
O
Profile owners
The real account holder of each profile. May or may not be the same person as the operator.
First design gate: is each profile used by its own owner?
LinkedIn's User Agreement keeps each account personal and does not allow one person to use another member's account. Owners handling their own login and 2FA is a good boundary, but it does not by itself make a workflow compliant. If a separate operator would act inside an owner's profile, that operating model has to be reviewed before production. We settle this on Day 1 of the pilot, before any build. LinkedIn User Agreement

Six Layers

1
Hosting
EU cloud hosts (Hetzner Germany or Finland are the reference prices). Cloud, local or hybrid is compared in Decisions. Host size is chosen from measured CPU, RAM, disk and bandwidth, plus one spare host so a single failure does not stop every workspace.
2
Workspace runtime
One isolated browser workspace per profile with its own storage. Runs either on client owned hosts (local launches) or as vendor cloud launches, which are limited per plan. Stored profiles, running workspaces and cloud launches are counted separately.
3
Identity and access
Company SSO with MFA for every operator and admin, workspace assignment per operator, and an audit log of who opened what. Infrastructure secrets live in a vault. Personal LinkedIn passwords and 2FA codes never reach infrastructure staff.
4
Network
Baseline without any proxy: SSO, MFA, firewall, TLS and a WireGuard VPN for admin access only. A proxy is added only where a specific approved need exists. It is not a security control, and the location written on a LinkedIn profile is a separate matter from the network path.
5
Monitoring and status
Host agents feed metrics and events into an alerting pipeline and the dashboard. Host health, workspace runtime and member session are tracked as separate fields. Member session stays UNKNOWN unless the owner confirms it or an approved feed exists.
6
Backup and recovery
Encrypted per workspace backups with keys owned by Aviovis, a restore drill in the pilot, and recovery targets (RPO and RTO) agreed with you rather than promised up front.

Monitoring Data Flow

Host agent→ Authenticated ingest→ Metrics and event store→ Alert rules→ Dashboard→ Acknowledge or escalate→ Audit export

Reference stack: Prometheus node exporter on each host, Alertmanager for routing, Grafana or a small custom view for operators. Every event carries timestamp, workspace, severity, source and a link to its runbook step. Final tool choice is confirmed in the pilot.

Security Controls

AreaProposed control
Sign inCompany SSO with MFA for every human user. Accounts are personal, never shared.
SecretsInfrastructure keys in a vault with rotation. Personal LinkedIn passwords and 2FA seeds are never stored by us.
Workspace dataEncrypted per workspace. Admin restore access only through a logged break glass step approved by the ops lead.
LogsTokens and personal data redacted. Audit log exported to storage admins cannot edit.
Joiners and leaversAccess granted through SSO groups, removed the same day someone leaves, reviewed monthly.
Data protectionAviovis as controller, us as processor under a data processing agreement. EU hosting; any non EU tool storage flagged before use.
IncidentsWritten response steps for lost devices, leaked keys and suspicious access, with contacts and timings.
